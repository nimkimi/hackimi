«Agent = Model + Harness» — LangChain
Hei. Jeg skal bruke ti minutter på den mest undervurderte delen av å utvikle med AI: harnessen. Hele presentasjonen er egentlig denne ene linja i praksis.

Samme modell. Helt forskjellig resultat.

mandag Kjørte testene med feil kommando, la koden i feil mappe, fant opp et mønster vi sluttet med i fjor
tirsdag Kjørte riktig testkommando, la filen i riktig mappe, stoppet før force push
Samme modell.
Typisk situasjon: du ber agenten fikse noe, og den kjører testene med feil kommando, legger filer i feil mappe, og finner opp et mønster dere gikk bort fra i fjor. Andre dager gjør samme modell alt riktig, og stopper til og med seg selv før en force push. Forskjellen ligger ikke i modellen. Den ligger i alt rundt den.

Harness: alt som ikke er modellen

harness = system prompt + tools + context + regler + feedback loops
  • Copilot CLI er en harness: agent loop, tools, filsystem
  • Men: den er generisk. Den kjenner ikke repoet deres.
harness tools context regler feedback
modell
Det rundt har et navn: harness. Alt som ikke er modellen. System-prompten, tools, tilgang til filsystem og terminal, context management, regler, feedback loops. Copilot CLI er i seg selv en harness: den tar en rå modell og gir den en agent loop, tools og et sted å jobbe. Men den er generisk. Den vet ingenting om akkurat vårt repo, våre konvensjoner, vår deploy. Modellen er motoren, harnessen er resten av bilen. Motoren får vi ikke gjort noe med, den leier vi. Resten av bilen er vår.

Harnessen kan vi bygge på, og jeg tenker på det som tre nivåer. Nivå null står vi allerede på: CLI-en rett ut av boksen, den forrige sliden. Nivå én er prose: du skriver tekst som styrer agenten, altså instructions og skills. Nivå to er programmatisk: du skriver kode som håndhever ting, hooks. Forskjellen mellom dem er den som betyr noe: prose er forslag, kode er garantier.

Skills: kunnskap on demand

.github/skills/deploy/SKILL.md
---
name: deploy
description: Slik deployer vi. Bruk ved
  release, rollback eller feilsøk av pipeline.
---
  • Instructions er alltid med → tar plass i context. Skills lastes når de er relevante.
  • Agenten ser bare navn + description, henter resten ved behov
  • Interop: leser også .claude/skills/
  • Samme gate: custom agents (.agent.md, subagent med eget context window og begrensede tools)
Men instructions har en kostnad: de er alltid med, i hver eneste prompt. Context window er begrenset, og alt dere dytter inn der konkurrerer om modellens oppmerksomhet. Ting den ikke trenger akkurat nå er støy. Skills løser det. En skill er en mappe med en SKILL.md, pluss eventuelt scripts og ressurser. Agenten ser bare navnet og beskrivelsen, og laster resten først når det er relevant for oppgaven. Kunnskap on demand. Typiske skills: deploy-rutinen deres, konvensjoner for internrammeverket, hvordan skrive en migrasjon. I samme gate finner dere custom agents: spesialiserte agenter med et avgrenset oppdrag og egne rettigheter, som en security-reviewer dere kaller på ved behov.

Hvorfor hooks, og ikke bare prose?

«Ikke push til main» i markdown er et ønske, ikke en regel.

1

Prose drukner: jo lengre session, jo dårligere etterlevelse

2

Prose koster context. Hooks koster null: de kjører utenfor modellen, hver gang

3

Guardrails må være garantier

Forbehold: krasjer hooken → kallet blokkeres (fail-closed). Timer den ut → slipper gjennom. Sett timeout, hold den rask.

Prose er kultur, hooks er lovverk.

prompt→ preToolUse
allow/deny/ask→ tool call→ postToolUse→ resultat→ svar

Alt til nå har vært prose, og prose har tre begrensninger. Én: modellen er probabilistisk, og i lange sessions begynner den å glemme regler. Jo mer context, jo lettere drukner de. To: prose koster context, det var derfor skills lastes on demand. En hook koster null context: den kjører utenfor modellen og fyrer hver gang, uansett hvor lang sessionen er blitt. Og den er billig, målt til rundt 35 millisekunder for en enkel hook. Tre: noen ting skal ikke være sannsynlige. For farlige kommandoer holder det ikke med 99 prosent etterlevelse. Siden dette er kode, hører feilmodusen med: krasjer hooken, blokkeres kallet. Timer den ut, slipper det gjennom. Så sett en timeout, og hold den rask. Mekanikken er enkel: en hook kjører på events i agent-loopen, og den viktigste er preToolUse. Den ser hvert tool call før det kjører, og svarer allow, deny eller ask. Tommelfingerregelen min: prose for det som krever skjønn, kode for det som aldri skal skje.

Hooks i praksis (testet på versjonen vi kjører)

~/.copilot/hooks/guard.json
{
  "version": 1,
  "hooks": {
    "preToolUse": [
      { "hooks": [ {
        "type": "command",
        "command": "bash ~/.copilot/hooks/guard.sh",
        "timeoutSec": 5
      } ] }
    ]
  }
}
guard.sh
#!/bin/bash
IN=$(cat)
if echo "$IN" | grep -q 'rm -rf'; then
  echo '{"permissionDecision":"deny",
    "permissionDecisionReason":
      "rm -rf er ikke lov her."}'
fi
exit 0
Denied by preToolUse hook: rm -rf er ikke lov her.

Typisk bruk

Guardrails med deny (rm -rf, git push --force, prod-credentials) · formatter/tester etter edit · context inn ved sessionStart

Sikkerhet

Repo-hooks kjører først når mappa er trusted · enterprise-policyer i policy.d kan ikke skrus av · disableAllHooks finnes

debug: /env viser lastede hooks · stdout → ~/.copilot/logs/ · lastes ved session-start · Windows: egne bash- og powershell-nøkler

Sånn ser det ut i praksis, og dette er testet på versjonen vi faktisk kjører. Én JSON-fil som sier: før hvert tool call, kjør dette scriptet, fem sekunders timeout. Og scriptet er seks linjer bash: les input, sjekk etter rm minus rf, svar deny med en begrunnelse. Det er alt. Nederst ser dere hva som skjer når agenten prøver seg: den får beskjed, med begrunnelsen vår. Samme mekanikk brukes til mer enn guardrails: kjør formatter og tester etter hver edit, eller injecter git status ved session start så agenten starter orientert. Og to ting til de sikkerhetsbevisste: repo-hooks kjører først når mappa er trusted, så et fremmed repo dere kloner får ikke kjøre shell hos dere automatisk. Og på enterprise kan policyer legges sentralt, de kan ikke skrus av av brukeren.

Fra min egen verktøykasse

tiering-guard.sh

Denier subagent-kall uten eksplisitt modellvalg. Deny-meldingen inneholder regelen → agenten leser den, retter seg og prøver igjen.

context-budget-advisor.sh

Leser context-forbruket ved hver stopp, ber agenten runde av eller ta handoff ved 50 % og 75 % av vinduet.

Gjenbruk i Copilot:

"command": "bash ~/.claude/hooks/tiering-guard.sh"

Scriptet er det samme; feltnavnene inn/ut må matche verktøyet.

tiering-guard.sh · utdragClaude Code-format
deny() {
  jq -n --arg r "$1" '{hookSpecificOutput:
    {hookEventName:"PreToolUse",
     permissionDecision:"deny",
     permissionDecisionReason:$r}}'
  exit 0
}
model=$(printf '%s' "$input" | jq -r '.tool_input.model // empty')
[ -n "$model" ] && exit 0
deny "no explicit model on this dispatch -- tier it and re-issue"
To fra mitt eget oppsett, i Claude Code, samme konsept. Den første denier alle subagent-kall som ikke har valgt modell eksplisitt. Det fine er at deny-meldingen inneholder selve regelen. Agenten leser den, retter seg og prøver igjen. Ingen spør meg om noe, den oppdrar seg selv. Den andre leser context-forbruket ved hver stopp, og ber agenten runde av eller ta handoff når vi passerer 50 og 75 prosent av vinduet. Begge er vanlige shell-scripts som JSON-en peker på. Skulle jeg flytte dem til Copilot, gjenbruker jeg scriptene som de er. Det som må matche er feltnavnene inn og ut, ikke koden.

Gi agenten sensorer

guides→ agent loop ←sensors

Guides styrer førnivå 1

Instructions, skills: øker kvaliteten på første forsøk

Sensors fanger opp etternivå 2

Tester, lint, typecheck via hooks: agenten retter seg selv

Dårlig output er ofte en manglende sensor.
Helt i starten definerte vi harness med feedback loops på lista. Det er den siste brikken. En agent er bare så god som feedbacken den får: tester, linter, typecheck, build-output er øynene dens. Uten dem gjetter den, med dem retter den seg selv. Birgitta Böckeler hos Thoughtworks kaller det guides og sensors, og det mapper rett på trappa vår. Guides styrer agenten før den handler: instructions og skills, prose-nivået. Sensors fanger opp feil etterpå: for eksempel hooks som kjører testene og dytter resultatet tilbake. Neste gang agenten leverer noe dårlig, sjekk om den hadde mulighet til å oppdage feilen selv. Som regel hadde den ikke det. Da er det ikke modellen det står på, det er en sensor som mangler.
